# GEO Monitoring

面向品牌可见度监测的 GEO 采集系统。项目通过 Playwright 操作国内 AI 平台的 Web 页面，保存回答、引用来源、分享链接和页面证据，并按品牌统计出现率、来源引用率及平台表现。

## 当前能力

- 以品牌为监测主体，维护品牌名、别名、产品和自有域名。
- 为品牌批量添加监控问题。
- 支持 DeepSeek、豆包、Kimi、千问、文小言和腾讯元宝共 6 个平台。
- 多账号登录态（Profile）模型：同一平台可维护多个账号，登录目录互不共享，按健康度自动选择。
- 动态共享队列：任务按平台串行领取，采用租约 + 心跳机制，Worker 异常退出后未完成任务可自动回收重跑。
- 分享链接采集：回答生成后可尝试采集公开分享链接，标记为 `captured`、`unavailable` 或 `failed`。
- 账号受限检测：识别登录失效、验证码拦截与账号风控，并给出明确的中文提示。
- 品牌提及分析：统计品牌名、别名在回答中的出现次数，并分析自有域名来源的引用覆盖情况。
- 支持按平台选择有头或无头模式；豆包默认有头，其余平台默认无头。
- 可选附加搜索提示词，要求模型先搜索公开来源后回答。
- 全局并发数可设为 1–6，同一平台最多同时执行一个问题。
- 采集回答原文、回答链接、引用 URL、引用次数、分享链接、截图、HTML 和来源 JSON。
- 使用 SQLite 保存品牌、问题、任务、回答、来源、事件和登录态。
- 提供品牌总览、监控任务、来源中心、趋势、报告和平台与登录状态页面。

## 技术栈

- Node.js 20+
- Fastify
- SQLite / better-sqlite3
- Playwright
- React 19 + Vite

## 快速开始

### 1. 安装依赖

```bash
npm install
```

采集器默认使用操作系统已安装的 Chrome 或 Edge。Windows 会自动检测常用安装路径；其他系统或自定义安装位置需要配置：

```bash
# Linux 示例
export GEO_BROWSER_PATH=/usr/bin/google-chrome
```

### 2. 初始化平台登录

每个平台都需要先完成一次人工登录，采集时复用该登录态。推荐在网页端按「平台 + 账号」维护登录态：

1. 打开「平台与登录状态」页面，左侧选择「全部平台」查看汇总，或直接切换到目标平台。
2. 点击右上角「添加账号」，填写手机号或登录账号（可填备注），点击「添加并登录」。
3. 系统会创建该账号专属的登录态，并立即弹出可见浏览器窗口；在窗口中完成登录后关闭窗口。
4. 关闭时如果仍停留在登录页面，该登录态会被标记为「已过期」，重新登录即可。

右侧账号列表按行列出该平台下的全部账号（状态、最近登录、最近使用），行内可以「登录」/「重新登录」与「停用」。页面顶部的「正在登录」面板会显示等待人工操作的会话，也可以直接点「关闭窗口」结束。

同一个平台的登录窗口和采集任务不能同时使用同一账号，否则 Chrome 会因 Profile 锁而启动失败。

登录态只能通过网页端创建：没有账号就没有登录态，平台会显示「无」，对应平台的监控任务会以 `login_required` 失败并给出中文提示。

### 3. 开发模式

分别启动后端和前端开发服务器：

```bash
# 终端 1：API，默认 http://127.0.0.1:3030
npm run dev

# 终端 2：前端，默认 http://127.0.0.1:5173
npm run web
```

Vite 会把 `/api` 和 `/artifacts` 代理到后端。

### 4. 生产模式

```bash
npm run build:web
npm start
```

前端构建完成后，Fastify 会在同一端口提供前端页面、API 和证据文件。可通过 `HOST`、`PORT` 和 `GEO_BROWSER_PATH` 调整监听地址、端口及浏览器路径：

```bash
HOST=0.0.0.0 PORT=3030 GEO_BROWSER_PATH=/usr/bin/google-chrome npm start
```

对公网提供服务时，应在应用前部署带 HTTPS 和身份认证的反向代理，不建议直接暴露 Fastify 端口。

## 登录态（Profile）模型

| 项目 | 说明 |
| --- | --- |
| 唯一标识 | Profile ID 由账号派生：手机号归一化为 E.164 形式，其他账号按 NFKC 归一化后取小写，保证同一账号始终映射到同一个 Profile |
| 存储目录 | `data/profiles/<platform>/<profileId>/chrome`，每个账号一个独立目录，Cookie 与 LocalStorage 互不覆盖 |
| 健康状态 | `new` 新建未登录、`ready` 可用、`expired` 登录过期、`error` 采集出错、`restricted` 账号受限、`disabled` 已停用 |
| 自动选取 | 只有 `ready` 状态的 Profile 会被自动选中，并按「最久未使用优先」在同平台的多个账号间轮转，避免配额与风控计数全压在一个号上 |
| 缺登录态 | 平台没有账号、或没有 `ready` 的账号时，任务以 `login_required` 直接失败并给出中文提示，不会静默重试，也不会退回平台默认目录 |
| 任务成功 | 采集成功后自动把该 Profile 标记为 `ready` 并刷新最近使用时间 |
| 网页端登录 | 「平台与登录状态」页面左侧选「全部平台」或单个平台、右侧管账号，右上角「添加账号」即可创建登录态并打开登录窗口，关闭窗口后自动复验登录结果 |

「平台与登录状态」页面左侧可切换「全部平台」或单个平台；「全部平台」视图罗列所有平台的账号（表格带平台列）并汇总账号总数、可用、受限、待登录、已停用等指标，右侧支持新增账号、重新登录与停用登录态。

所有平台的登录方式统一为「弹出可见浏览器窗口 + 人工登录」：系统不区分密码登录、验证码登录等平台差异，登录窗口关闭后按是否仍停留在登录页判定登录态是否可用。

## 任务队列与租约

- 队列保存在 SQLite 中，多个 Worker 共享同一份待办列表，按平台串行领取任务。
- 领取任务时写入租约标识与租约过期时间，默认租约 120 秒。
- Worker 每 15 秒发送一次心跳续租，长任务不会因租约过期被重复领取。
- 租约过期且无心跳的任务会被自动回收，重新入队继续执行。
- 普通失败最多重试 3 次，超过上限后标记为最终失败。
- 账号受限与登录失效属于不可重试错误，会直接结束任务并把 Profile 置为 `restricted` 或 `expired`。

## 验证码与风控处理

平台风控经常在提交问题之后才弹出验证码，采集器按下面几层处理：

1. **持续探测**：打开页面时、以及等待回答期间每 5 秒探测一次登录态与验证码。平台风控几乎都是「提交问题之后」才弹验证码，只在打开页面时探测一次必然漏掉。除了通用验证码控件，还能识别阿里云内容安全（Baxia）的 punish iframe 与滑块、网易易盾的空间点选验证码（DeepSeek 使用）、极验（Geetest）等形态。
2. **无头快速失败**：无头模式命中验证码时立刻结束当前问题，不再消耗后续问题配额。
3. **转有头模式人工处理**：无头失败后自动用同一个登录账号重新打开可见浏览器窗口，由人工在窗口里把验证码过掉；验证码消失后继续等待回答，人工处理的时间不计入回答超时。人工处理期间浏览器窗口会一直等着，最多 3 分钟。
4. **平台进入人工窗口**：某平台撞过验证码后，接下来 30 分钟内该平台的任务**直接用有头模式执行**，遇到验证码就在窗口里等人工，不再走「无头失败 → 有头重跑」，避免同一条问题被提交两次、白白消耗平台配额（DeepSeek 就是这样被刷到禁言的）。窗口到期自动恢复无头，也可以在「平台与登录状态」页面点「恢复无头」提前解除。
5. **平台级熔断**：验证码属于平台风控而不是账号故障，因此不会把登录态改成异常；同一个平台连续 3 次遇到验证码后进入 30 分钟冷却，期间不再领取该平台的任务，剩余问题需要稍后重新发起监测。冷却可以在「平台与登录状态」页面点「立即恢复」解除。

平台**繁忙 / 排队**是另一类问题，单独处理：Kimi 高负载时会弹出「和Kimi聊天的人太多了，订阅会员可进入优先队列」，非会员进不了优先队列，回答永远不会生成。这种情况人工也解决不了，因此不会转有头模式、也不会重试，而是直接结束当前问题并让平台冷却 10 分钟，避免在繁忙期间反复提交。

| 失败类型 | 处理方式 |
| --- | --- |
| `human_challenge` | 当前问题标记为失败，账号保持可用，平台累计次数并可能进入冷却；不会像普通超时那样重试 3 次，避免在已被风控时继续硬刷 |
| `platform_busy` | 平台繁忙（排队），人工无法处理；当前问题标记为失败，平台冷却 10 分钟 |
| `login_required` | 登录态失效，账号标记为 `expired`，需要重新登录 |
| `account_restricted` | 账号受限，标记为 `restricted` 并停止使用该登录态 |

## 分享链接采集

回答生成后，采集器会尝试点击平台的分享控件并读取分享链接：

| 状态 | 含义 |
| --- | --- |
| `captured` | 成功采集到公开分享链接 |
| `unavailable` | 平台不提供分享或本次未找到分享入口 |
| `failed` | 已进入分享流程但读取链接失败 |

分享链接会随运行产物写入 `share.json`，并在证据抽屉中以可点击链接展示。

## 使用流程

1. 创建品牌并填写别名、产品或自有域名。
2. 在品牌下添加需要长期监控的问题。
3. 在「平台与登录状态」页面为每个平台添加账号并完成登录，确认登录态显示为「可用」。
4. 发起监控，选择问题、平台、浏览器模式和并发数。
5. 查看任务进度、回答原文、引用来源、分享链接及截图证据。
6. 在品牌总览、来源中心和趋势页持续对比监测结果。

## 目录结构

```text
geo-monitoring/
├─ src/
│  ├─ analysis/            # 品牌提及与自有域名引用分析
│  ├─ api/                 # Fastify 路由
│  ├─ config/              # 数据目录配置
│  ├─ db/                  # SQLite schema 与 repository
│  ├─ infrastructure/      # Playwright 执行器和证据文件
│  ├─ platforms/           # 各平台适配器
│  ├─ profiles/            # 账号标识归一化与登录态目录规则
│  ├─ worker/              # 任务队列、租约与并发调度
│  └─ index.js             # 服务入口
├─ web/                    # React 前端
├─ test/                   # 自动化测试
├─ docs/                   # 设计与部署文档
└─ data/                   # 本地数据库、Profile 和运行证据（不提交）
```

运行数据默认位于：

```text
data/
├─ brand-monitoring.sqlite
├─ profiles/<platform>/<profileId>/chrome
└─ artifacts/<run-id>/<platform-run-id>/
```

`data/`、数据库、浏览器 Profile、运行截图、`node_modules/`、`web/dist/`、`.xlsx-builder/` 和 `outputs/` 均已通过 `.gitignore` 排除。浏览器 Profile 含登录凭据，不能提交、公开或与不受信任的用户共享。

## 远端服务器登录

当前登录命令只会在运行后端的机器上打开有头浏览器。远端 Linux 场景计划使用 Xvfb + x11vnc + noVNC，把后端浏览器画面安全地提供到前端，同时复用现有 Playwright Profile。

详细方案见 [docs/remote-browser-login.md](docs/remote-browser-login.md)。

## 已知限制

- AI 平台页面结构会变化，适配器和引用提取规则需要持续维护。
- 平台风控、验证码和登录过期无法完全自动化，必要时需要人工重新登录。
- 有头/无头可用性取决于平台策略；豆包当前更适合使用有头模式。
- 任务队列数据持久化在 SQLite 中，但领取、租约续期与并发调度仍由单个 Node 进程维护；进程重启后过期租约会在下次领取时回收。
- 品牌名与别名的提及统计按出现次数累加，短别名可能同时匹配到长名称（例如「千威」会命中「千威云」）。
